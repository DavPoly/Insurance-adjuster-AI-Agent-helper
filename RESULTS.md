# Results

- **Run/test instructions:** From `starter-kit/`: `make setup` to build and start all services, `make test` to run the backend (`tests/backend`) and frontend (`tests/frontend`) unit suites, `make grade` to run the full public auto-grader (`make grade-smoke` for a faster 3-case subset while iterating), `make eval` to run the `search_past_claims` retrieval-quality eval (`backend/evals/`). `make grade` and `make eval` need the real `OPENROUTER_API_KEY` and a running Docker daemon. All figures below were measured on the deterministic pipeline unless labelled pre-refactor.

- **Architecture and model-call budget:** Claim triage runs a fixed five-stage deterministic pipeline with no model in its control loop: (1) one multimodal Jev 1.14 decision call for intake validation and parameter extraction (`damage_type`, `severity`, `affected_areas`), (2) three deterministic tools (`search_past_claims`, `estimate_repair_cost`, `check_coverage`) called directly, (3) one generative LLM call for synthesis, (4) one text-only Jev 1.14 decision call for output safety (bounded to three attempts → `422`), (5) response terminal. The nominal (per-successful-pass) budget is therefore **1 LLM call + 2 Jev calls**, down from roughly 10 LLM calls in the removed ReAct loop; if the output-safety retries are exhausted, the bounded worst case is **3 LLM calls + 4 Jev calls** (three synthesis calls, three safety checks, and the one intake decision).

- **Models and embedding method:** The generative LLM is an OpenAI-compatible model served via OpenRouter (`LLM_MODEL`, `OPENROUTER_API_KEY`, `OPENROUTER_BASE_URL` in `starter-kit/.env`), used for the single synthesis call only. The Jev 1.14 decision model is served via OpenRouter's Decisions API (`DECISION_MODEL`, `DECISION_ENDPOINT`, reusing the same `OPENROUTER_API_KEY`); Jev answers typed `noul`/`choice` questions with calibrated probabilities and generates no text. Embeddings use a local `sentence-transformers` model, `BAAI/bge-small-en-v1.5` (no external embedding API), one combined embedding per historical claim, built from the claim description and adjuster notes together rather than embedded separately.

- **Cost and latency character of the decision model:** Per its provider, Jev is billed **on input tokens only** and a decision call takes roughly **200–300 ms**. Requests that carry an image run in Jev's **long-context mode** (slower and less accurate), and image input is an "early feature" of Jev 1.14. These are provider characteristics, not measurements from this repository; the end-to-end latency below is the measured figure.

- **Agent trace:** `GET /api/v1/agent/trace/{claim_id}` returns 18 `reason`/`act`/`observe` steps (6 operations × reason/act/observe) reconstructed from the deterministic pipeline's own step records — **not** from a model's message history. It is an execution trace of the fixed pipeline, not a model-in-the-loop ReAct trace.

- **Test cases exercised, passing checks and remaining failures:** 154 unit tests passing, 0 failing (135 in `tests/backend`, 19 in `tests/frontend`, via `make test`). Public auto-grader (`make grade`): 27/29 checks passing, 2 skipped, 0 failed — infrastructure 12/14 (2 skipped), RAG 3/3, accuracy 5/5, guardrails 7/7. The 2 skips are `test_ui_has_form_elements` and `test_ui_has_results_area` in `auto-grader/tests/test_ui.py`: Chainlit's UI is a client-rendered SPA, so the grader's static (non-JS) HTML parsing can't see the real form/results elements and skips rather than fails. This is left as a skip rather than worked around, so the grader reports the run as incomplete pending browser review.

- **Auto-grader score:** **13.57/14** automated (infrastructure 2.57/3, RAG 4/4, accuracy 4/4, guardrails 3/3); the manual maximum is 80. The published agent-loop category (weight 6) and its ReAct-structure checks were removed along with the ReAct requirement (see `auto-grader/grade.py` and `auto-grader/README.md`), so the automated maximum is 14 rather than 20. The pre-refactor score of 19.57/20 (33/35 checks, 2 skipped) was scored against the old maximum and is **not** comparable.

- **Automated report location:** `auto-grader/results/grade_report.json` (category breakdown and auto score) and `auto-grader/results/accuracy_full.json` (per-case timings and accuracy metrics).

- **Accuracy results on the provided development set and number of attempted cases:** Full 35-case development set, all 35 attempted and returned (0 failures). Damage-type accuracy 0.914 (min threshold 0.5), severity score mean 0.871 (min threshold 0.4), repair-cost midpoint accuracy mean 0.654 (min threshold 0.3). For comparison, the pre-refactor ReAct pipeline scored 0.971 / 0.814 / 0.637. The repair cost is the per-area cost for `damage_type` × `severity` multiplied by the affected-area count, so the cost score depends on getting all three right. Two node-1 rules carry most of it: affected areas keep only the most specific label (no `wall`/`ceiling`/`interior`/`exterior` alongside the room they restate), and each severity level has its own definition in the Jev choice criteria. Before the surface/component area rules and the severity definitions, the same pipeline scored 0.275 on cost. The severity definitions were calibrated against this development set, so these figures are optimistic for unseen claims.

- **RAG retrieval quality (`make eval`, not part of the auto-grader):** 14 hand-written adjuster-style queries (`backend/evals/claim_search_queries.py`) run against `search_past_claims` with the real knowledge base and real embedding model. Recall@5 100%, mean reciprocal rank 0.952 — 13/14 queries found an expected claim at rank 1, 1/14 at rank 3. Re-run after the refactor with identical results; `search_past_claims` and the embedding path are unchanged.

- **End-to-end latency (P50, sample size, measurement method):** **5,419.4 ms**, n=35 (the full accuracy run above), measured client-side end-to-end by the auto-grader's accuracy harness timing each `POST /api/v1/claims/triage` call, which includes application logic, model calls, tool calls and network round-trip, not just model inference. The pre-refactor ReAct pipeline measured 18,490.4 ms on the same harness.

- **Full or smoke run and successful/failed requests:** Full run (`make grade`, not smoke) — 35/35 accuracy requests succeeded (HTTP 200), 0 failed; 27/29 total auto-grader checks passed, 2 skipped (see above), 0 failed.

- **Important assumptions, limitations and unfinished requirements:** The pipeline trades the ReAct loop's flexibility for a fixed tool sequence. That is correct here because the tool order is fully determined by the claim's fields, but a future tool whose use depends on intermediate results would need the pipeline extended rather than a prompt changed. Every "intelligent" step is now either a deterministic tool or a typed Jev decision call except the one synthesis call. Jev's visual property-damage detection is a general model, not tuned to this corpus, and image-carrying requests run in Jev's slower, less accurate long-context mode. When a claim is submitted with only an image, `search_past_claims` runs on the empty description, so it returns the same "similar past claims" for every photo. Claims and traces are still kept in-memory — fine for a single demo, but they do not survive a restart or scale across instances. The combined description+notes embedding is kept for simplicity; it has not caused measurable relevance problems at this corpus size, but it has not been stress-tested either.

- **What I would do next:** Build the `search_past_claims` query from the node-1 classification when no description is submitted. Validate the severity definitions on claims outside the development set. If the tool sequence ever stops being fully predictable, add back a bounded decision step rather than a full ReAct loop. If the knowledge base grows significantly, revisit the single combined-embedding-per-claim design against separate description/notes embeddings. Move claim/trace storage to durable, shared storage if this moves beyond a single-session demo.

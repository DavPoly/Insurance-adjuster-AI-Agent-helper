# Results

- **Run/test instructions:** From `starter-kit/`: `make setup` to build and start all services, `make test` to run the backend (`tests/backend`) and frontend (`tests/frontend`) unit suites, `make grade` to run the full public auto-grader (`make grade-smoke` for a faster 3-case subset while iterating), `make eval` to run the `search_past_claims` retrieval-quality eval (`backend/evals/`).
- **Models and embedding method:** LLM is an OpenAI-compatible model served via OpenRouter (`LLM_MODEL`, `OPENROUTER_API_KEY`, `OPENROUTER_BASE_URL` in `starter-kit/.env`), used for intake validation, the ReAct triage loop, and output synthesis/safety checks. Embeddings use a local `sentence-transformers` model, `BAAI/bge-small-en-v1.5` (no external embedding API), one combined embedding per historical claim, built from the claim description and adjuster notes together rather than embedded separately.
- **Test cases exercised, passing checks and remaining failures:** 98 unit tests passing, 0 failing (79 in `tests/backend`, 19 in `tests/frontend`, via `make test`). Public auto-grader (`make grade`): 33/35 checks passing, 2 skipped, 0 failed, across all five categories — auto score 19.57/20. The 2 skips are `test_ui_has_form_elements` and `test_ui_has_results_area` in `auto-grader/tests/test_ui.py`: Chainlit's UI is a client-rendered SPA, so the grader's static (non-JS) HTML parsing can't see the real form/results elements and skips rather than fails. This is left as a skip rather than worked around.
- **Automated report location (if run):** `auto-grader/results/grade_report.json` (category breakdown and auto score) and `auto-grader/results/accuracy_full.json` (per-case timings and accuracy metrics).
- **Accuracy results on the provided development set and number of attempted cases:** Full 35-case development set, all 35 attempted and returned (0 failures). Damage-type accuracy 0.971 (min threshold 0.5), severity score mean 0.814 (min threshold 0.4), repair-cost midpoint accuracy mean 0.637 (min threshold 0.3).
- **RAG retrieval quality (`make eval`, not part of the auto-grader):** 14 hand-written adjuster-style queries (`backend/evals/claim_search_queries.py`) run against `search_past_claims` with the real knowledge base and real embedding model. Recall@5 100%, mean reciprocal rank 0.952 — 13/14 queries found an expected claim at rank 1, 1/14 at rank 3.
- **End-to-end P50 latency in milliseconds, sample size and measurement method:** 18,490.4 ms, n=35 (the full accuracy run above). Measured client-side, end-to-end, by the auto-grader's accuracy harness timing each `POST /api/v1/claims/triage` call, which includes application logic, model calls, tool calls and network round-trip, not just model inference.
- **Full or smoke run and successful/failed requests:** Full run (`make grade`, not smoke) — 35/35 accuracy requests succeeded (HTTP 200), 0 failed; 33/35 total auto-grader checks passed, 2 skipped (see above), 0 failed.
- **Important assumptions, limitations and unfinished requirements:** Currently, an LLM call backs every "intelligent" step (validation, ReAct reasoning, synthesis) rather than deterministic logic where possible, which is the main driver of the ~16-40s per-claim latency and the biggest cost/latency lever left unaddressed. Secondly, the claims and agent traces are kept in-memory, which is fine for a single demo but it won't survive a restart or scale across instances. Lastly, the combined description+notes embedding was chosen for simplicity purposes over a more elaborate retrieval design, but this hasn't caused measurable relevance problems at this corpus size, altough it hasn't been stress-tested either.
- **What I would do next:** I think the biggest next step would be to profile which ReAct steps actually need a full LLM call versus a cheaper deterministic check, to cut both latency and cost. Then, I would tighten the validation and ReAct prompts to reduce token usage per step. If the knowledge base grows significantly, we would need to revisit single combined-embedding-per-claim against separate description/notes embeddings to see if retrieval relevance changes. Last improvement would be to move claim/trace storage to durable, shared storage if this moves beyond a single-session demo.
